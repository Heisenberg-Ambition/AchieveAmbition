# Legacy Salvation 总结

## 一、Java 与 C++ std::regex 的正则差异

**谱系**：Java 正则 → Perl 系（PCRE-ish，回溯型）；C++ std::regex → ECMAScript / POSIX 系（标准化、弱化版）。

基础积木（`.` `*` `+` `?` `[]` `()` `|` `^`）两边共通，约 80% 简单正则可移植；差异集中在高级能力：

| 能力                                               | Java                    | C++ std::regex（默认 ECMAScript）         |
| -------------------------------------------------- | ----------------------- | ----------------------------------------- |
| 环视断言 `(?=...)` `(?!...)` `(?<=...)` `(?<!...)` | ✅ 支持                 | ❌ 不支持                                 |
| 命名捕获组 `(?<name>\d+)`                          | ✅ 支持                 | ❌ 不支持，只能数字编号                   |
| 懒惰量词 `.*?` `.+?`                               | ✅ 支持                 | ⚠️ 部分实现支持，GCC/libstdc++ 行为不一致 |
| Unicode（`\p{L}`、`\p{Han}` 等）                   | ✅ 原生 UTF-16 完整支持 | ❌ 非常有限，依赖 locale，实践几乎不可用  |

**判断法则**：正则里出现 `(?`，大概率不是 std::regex 能跑的。

**C++ 工程替代方案**：

| 场景              | 推荐                 |
| ----------------- | -------------------- |
| 纯标准 C++        | std::regex（能力弱） |
| 要 Java/Perl 行为 | PCRE / PCRE2         |
| 线性时间保证      | RE2                  |
| ROS / 工程常用    | PCRE2                |

## 二、Java `String.matches()` 的全串匹配陷阱

**现象**：同一正则 `[A-Za-z]+\d`，Java 只匹配"若干字母 + 一个数字"，其他语言却匹配"字母 + 多个数字"。

**真相**：

- Java 的 `matches()` 要求**整个字符串完全匹配**，等价于 `^regex$`
- 其他语言默认是**子串匹配（search/find）**，只找一段满足的子串

所以 `abc12`：matches() → ❌（多出 2）；子串搜索 → ✅（`abc1` 就满足）。

**结论**：不是正则语法不同，而是"API 定义匹配范围"。正则定义"规则"，API 定义"匹配范围"。

**Java 内正确姿势**：

- 验证格式 → `matches()`
- 搜索片段 → `Pattern p = Pattern.compile(...); Matcher m = p.matcher(s); m.find();`

## 三、懒惰量词（Lazy / Reluctant Quantifier）

**贪婪**：能多吃就多吃，先全吞再回头调整。`"a123b456b".replaceAll("a.*b", "X")` → `X`（吞到最后一个 b）。

**懒惰**：量词后加 `?`，能少吃就少吃，整体匹配成功即停。`a.*?b` 匹配 `a123b`。

| 贪婪 | 懒惰 | 含义                 |
| ---- | ---- | -------------------- |
| `*`  | `*?` | 0 次或更多（尽量少） |
| `+`  | `+?` | 1 次或更多（尽量少） |
| `?`  | `??` | 0 或 1 次（优先 0）  |

工程示例：匹配 HTML 标签 `<div>.*?</div>`（懒惰）一次只匹配一个标签；`<div>.*</div>`（贪婪）会吞掉整个字符串。

**关键提醒**：懒惰 ≠ 快。懒惰/贪婪是匹配策略，性能取决于回溯路径，有时懒惰反而更慢——这正是 C++/RE2 限制它的原因。

## 补充与纠正

1. **std::regex 语法细节**：C++ std::regex 实际支持**多种语法**（ECMAScript / basic / extended / awk / grep / egrep），默认 ECMAScript。ECMAScript 模式其实**支持**部分非贪婪量词（`*?`、`+?`、`??`）和零宽断言**并不**——断言确实不支持，非贪婪量词在 ECMAScript 语法下是支持的。原文本"部分实现支持"的表述在 GCC 上也存在 bug 历史，用 PCRE2 更稳。**重要纠正**：非贪婪量词属于 ECMAScript 标准语法，GCC/libstdc++ 对 `.*?` 的支持是**可用的**，只是历史上对某些复杂组合（如与 `$`/`\b` 配合或嵌套量词）有 bug。
2. **Java matches() 的等价性**：`"abc123".matches(...)` 等价于 `Pattern.compile(...).matcher("abc123").matches()`；注意 `Matcher.matches()` 与 `Matcher.find()` 是同一 Pattern 下的两种模式，`find()` 内部有 last 位置状态，循环调用需注意 `region`/`reset`。
3. **懒惰量词与性能**：`.*?` 在长输入 + 回溯型引擎下可能产生大量回溯（如嵌套 HTML 场景），这是 RE2 用线性时间模型放弃回溯的原因；PCRE2 可通过 DFA match 或原子组/占有量词优化。
4. **Java 的 Unicode 是 UTF-16 代理对**：Java char 为 16 位，补充平面字符（如 emoji）占两个 char，`\p{...}` 与 String 长度计算均受此影响。
